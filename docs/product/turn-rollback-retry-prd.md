# 回滚本轮并重试 PRD

## 1. 背景

当前项目已经支持多 Runtime Agent Workbench，单轮 assistant 执行不仅会产出文本，还可能对工作区产生真实副作用，例如：

- 读取文件
- 编辑文件
- 创建文件
- 删除文件
- 执行命令
- 生成产物

因此，Coding Agent 场景中的“重试”不能等同于普通聊天产品里的“重新生成文本”。

如果不恢复工作区状态，直接对同一条用户消息重新执行，可能带来：

- 重复 patch
- 重复新增文件
- 再次覆盖原文件
- 在错误结果上继续累加修改

本需求聚焦于一种更严格的能力：

> 回滚本轮并重试

即：先恢复本轮执行前的工作区状态，再重新执行这一轮用户请求。

---

## 2. 目标

### 2.1 产品目标

提供一个对标 Claude Code / Codex 类产品心智模型的安全重试能力，使用户可以：

- 对某一轮执行结果不满意时，一键撤销本轮工作区修改
- 在“像这一轮没发生过”的前提下重新执行
- 避免重复叠加文件副作用

### 2.2 用户价值

用户不需要手动：

- 找出本轮改了哪些文件
- 手动回退 patch
- 再重复输入请求

而是通过统一入口完成：

1. 触发重试
2. 轻量确认机制
3. 系统自动回滚本轮
4. 自动重新执行

---

## 3. 非目标

本期不做：

- 编辑后继续
- 保留当前结果并分叉重做
- 多轮批量回滚
- Git 分支级回滚
- 数据库 / HTTP 写操作 / 外部系统副作用回滚
- 进程状态回滚
- 依赖环境回滚（如 `npm install` / `pip install`）

本期只聚焦：

> 单轮 Turn 的工作区文件回滚 + 自动重试

---

## 4. 核心定义

### 4.1 Turn

一个 Turn 指一次完整的用户请求执行回合，包括：

- 一条 user message
- 本轮产生的 tool steps
- 本轮 touched files
- 本轮 artifacts
- 本轮 assistant message
- 本轮 runtime session 关联信息

### 4.2 回滚本轮并重试

语义定义：

> 将工作区恢复到“本轮开始前”的状态，然后使用同一条用户消息重新执行一轮新的 Agent run。

这意味着：

- 回滚的是工作区状态
- 重试的是该轮用户意图
- 新的一轮会生成新的 steps / artifacts / assistant message
- 老的一轮在会话中保留，但标记为“已回滚”

---

## 5. 设计原则

### 5.1 单入口原则

交互入口与当前的重试 icon 保持一致，不新增独立入口，不做入口差异化。

即：

- 仍然使用 assistant 消息操作区中的重试 icon
- 用户点击这个 icon 时，执行的是“回滚本轮并重试”语义

这样可以保持界面简洁，避免给用户额外认知负担。

### 5.2 轻量确认原则

不做重弹窗、复杂多选菜单或二级决策流。

点击重试 icon 后，仅做轻量提示，让用户知道：

- 系统将撤销本轮工作区修改
- 然后重新执行该轮请求

### 5.3 保守安全原则

只有在可安全回滚时，才允许真正执行。

若检测到冲突或不可回滚副作用：

- 不静默覆盖
- 不假装重试成功
- 明确告知用户无法安全回滚

### 5.4 可追溯原则

被回滚的旧 Turn 不能直接消失。

需要保留会话历史，让用户知道：

- 哪一轮被回滚了
- 当前展示的是重新执行后的新结果

---

## 6. 用户场景

### 场景 A：Agent 改错文件

用户让 Agent 更新某个文档，Agent 改到了错误目录。

用户点击重试 icon，系统先撤销本轮文件变更，再重新执行这轮请求。

### 场景 B：本轮方向错误

Agent 已经改了若干文件，但实现方向明显偏了。

用户不希望在错误结果上继续修补，而是希望从本轮前状态重新跑。

### 场景 C：避免重复 patch

如果只是重新跑同一条消息，Agent 可能在现有结果基础上继续改，造成重复插入或二次覆盖。

回滚后重试可以避免这类累加副作用。

---

## 7. 产品方案

### 7.1 交互入口

使用当前 assistant 消息操作区中的重试 icon 作为唯一入口。

不新增单独按钮，不增加菜单层级。

#### 交互语义

当用户点击当前重试 icon 时，产品语义为：

> 回滚本轮并重试

#### Tooltip 建议

可将 tooltip 从“重试”调整为更准确但仍简洁的文案，例如：

- `回滚并重试`
- `撤销本轮并重试`

推荐使用：

- `回滚并重试`

---

### 7.2 轻量提示机制

点击 icon 后，不使用重型弹窗。

推荐轻量交互：

#### 方案 A：Popover 确认

在 icon 附近出现一个轻量浮层，内容示例：

标题：
- `回滚本轮并重试？`

说明：
- `会撤销本轮对工作区文件的修改，然后重新执行该请求。`

按钮：
- `确认`
- `取消`

这是本期推荐方案。

#### 方案 B：第一次提示，后续直接执行

也可作为后续增强：

- 第一次点击时展示轻量说明
- 用户确认后记住偏好
- 后续直接执行

本期先不做。

---

### 7.3 触发前检查

点击确认后，系统先判断该 Turn 是否满足可回滚条件。

只有满足以下条件才执行：

- 本轮有完整的 touched files 记录
- 对每个文件变更保存了回滚所需信息
- 当前文件状态未与后续人工修改冲突
- 本轮未包含超出本期能力范围的不可自动回滚副作用

如果不满足，则不给执行，并以轻量提示告知原因。

提示示例：

- `无法安全回滚：有文件已在本轮之后被修改`
- `无法安全回滚：本轮包含不可自动撤销的外部副作用`

---

### 7.4 执行流程

用户确认后，系统执行以下流程：

#### Step 1：冻结当前 Turn

将当前 Turn 标记为处理中，避免重复点击。

#### Step 2：执行回滚

对本轮 touched files 逐一恢复到 `before` 状态：

- `update` → 恢复旧内容
- `create` → 删除新增文件
- `delete` → 恢复被删文件
- `rename` → 恢复原路径与原内容

#### Step 3：校验回滚结果

确认工作区已恢复到该 Turn 开始前的基线状态。

#### Step 4：标记旧 Turn 状态

将旧 Turn 标记为：

- `rolled_back`

并在会话中保留。

#### Step 5：重新执行

使用同一条用户消息重新发起一次新的 Agent run：

- 新的 turn_id
- 新的 assistant message
- 新的 steps
- 新的 touched files 记录

#### Step 6：展示结果

新一轮结果正常展示在会话中。

---

## 8. UI 展示方案

### 8.1 旧 Turn 状态展示

被回滚的旧 assistant 消息不应直接消失。

建议保留，但以弱化态展示：

- 灰态或低强调样式
- 标签：`已回滚`
- 工具步骤可折叠
- 可查看本轮改动摘要（后续增强）

目的：

- 保留会话可追溯性
- 让用户理解系统已执行回滚

### 8.2 新 Turn 展示

新一轮正常展示为最新执行结果。

可以加一个弱提示标签，例如：

- `重新执行`

但不强制。

### 8.3 执行中状态

点击确认后，当前消息卡片进入处理中状态：

- 重试 icon disabled
- 显示轻量 loading
- 文案：`正在回滚并重试...`

### 8.4 失败状态

如果回滚失败，在旧 Turn 下展示错误提示：

- `无法安全回滚本轮`
- 原因说明
- 冲突文件数量或冲突原因摘要

## 9. 数据模型方案

## 9.1 Turn 基础结构

建议引入 Turn 级元数据：

```text
Turn
- turn_id
- session_id
- user_message_id
- assistant_message_id
- runtime_id
- model_id
- status: running / done / error / rolled_back / rollback_failed
- created_at
- completed_at
```

## 9.2 文件变更记录

每个 Turn 记录文件变更明细：

```text
TurnFileChange
- path
- operation: create | update | delete | rename
- before_content
- after_content
- before_hash
- after_hash
- old_path
- new_path
```

要求：

- 必须能恢复 `before`
- 必须能判断当前文件是否仍等于该 Turn 的 `after`

## 9.3 副作用级别

每个 Turn 增加副作用级别：

```text
side_effect_level
- none
- workspace_reversible
- workspace_conflicted
- external_irreversible
```

用于决定是否允许“回滚并重试”。

---

## 10. 冲突检测规则

### 10.1 冲突产生原因

典型情况：

1. 第 N 轮修改了 `a.ts`
2. 用户手动又修改了 `a.ts`
3. 用户再点击“回滚并重试”

若系统直接恢复 `before`，会覆盖用户后续手动修改。

因此必须先检测冲突。

### 10.2 核心判断逻辑

对每个 touched file：

- 若当前文件内容 == `after_content` 或 `after_hash`
  - 可安全回滚
- 若不一致
  - 视为冲突
  - 阻止自动回滚

### 10.3 不同操作类型的判定

#### create

- 如果文件仍存在且内容等于 `after`
  - 可删除回滚
- 如果内容已变化
  - 冲突

#### update

- 如果当前内容等于 `after`
  - 可恢复为 `before`
- 如果不等于
  - 冲突

#### delete

- 如果文件当前不存在
  - 可恢复
- 如果文件已被重新创建
  - 冲突

#### rename

- 原路径/新路径状态与记录不一致
  - 冲突

---

## 11. 可回滚范围

本期支持：

- 工作区内文本文件的 `create / update / delete / rename`

本期不保证自动回滚：

- `npm install` / `pip install` 带来的环境变化
- 后台进程状态
- 数据库写入
- HTTP 写请求
- 外部系统调用
- 系统级副作用

若本轮包含这些行为，则应阻止“回滚并重试”，并给出轻量说明。

---

## 12. Runtime 兼容策略

## 12.1 总原则

回滚语义由 Workbench 外层统一实现，不依赖 Runtime 原生的“resume”或“history rewind”能力。

即：

- Runtime 负责执行
- Workbench 负责记录 Turn 文件变更
- Workbench 负责回滚
- 回滚完成后再发起新一轮运行

## 12.2 Handmade Runtime

第一期最适合优先支持：

- 工具链可控
- 文件变更容易全量记录
- 回滚能力最容易做完整

## 12.3 Claude Code / OpenCode Runtime

这些 Runtime 更适合“继续会话”，不天然提供“回到本轮之前”的严格语义。

因此：

- 不依赖其 native session 做回滚
- 由外层基于 TurnFileChange 做工作区恢复
- 再重新发起新一轮执行

---

## 13. 失败处理

### 13.1 回滚失败

状态标记为：

- `rollback_failed`

前端展示：

- `无法安全回滚本轮`
- 原因摘要
- 保留旧结果

### 13.2 重试失败

如果回滚成功但新一轮执行失败：

- 旧 Turn = `rolled_back`
- 新 Turn = `error`

这样会话历史仍可追踪。

---

## 14. 埋点建议

建议埋点以下事件：

### 用户行为

- 点击重试 icon
- 看到轻量确认提示
- 确认执行
- 取消执行

### 系统结果

- rollback_success
- rollback_conflict
- rollback_failed
- retry_run_success
- retry_run_failed

### 核心指标

- 回滚成功率
- 冲突率
- 重试后二次完成率
- 平均每轮 touched files 数量

---

## 15. 分阶段落地建议

### Phase 1：基础版

范围：

- 仅支持 handmade runtime
- 仅支持文本文件 create / update / delete
- 可安全回滚时允许执行
- 有冲突时阻止执行
- 前端使用当前重试 icon + 轻量 Popover 提示

验收标准：

- 用户点击重试 icon 后能看到轻量说明
- 可回滚 Turn 能成功恢复工作区并重新执行
- 冲突场景下不会覆盖用户后续修改
- 被回滚 Turn 在会话中有状态标记

### Phase 2：增强版

范围：

- 增加 rename 支持
- 增加查看本轮改动摘要
- 支持 Claude Code / OpenCode adapter 接入统一回滚机制

---

## 16. 推荐产品决策

本期建议采用以下明确策略：

1. 使用当前重试 icon 作为唯一入口
2. 将其真实语义定义为“回滚本轮并重试”
3. 采用轻量 Popover 说明，而不是重弹窗
4. 仅在可安全回滚时允许执行
5. 回滚能力只承诺“工作区文件级”，不承诺外部副作用撤销

---

## 17. 最终结论

对于会改文件的 Agent，“重试”不应再被理解为普通聊天产品里的 regenerate。

本期产品定义为：

> 使用现有重试 icon 作为单入口，在轻量提示后执行“回滚本轮并重试”。

其核心是：

- 把单轮执行视为一个带副作用的 Turn
- 记录本轮文件变更
- 在重试前恢复到 Turn 开始前状态
- 对冲突和不可逆副作用采取保守策略
- 在保证界面简洁的同时，向用户轻量说明重试机制
